1 哲学: 検証 ≠ テスト

このアーキテクチャは、たったひとつのメンタルモデルの上に成り立っています。

検証とは、表層における実行時の観測である。

アプリをビルドし、実行し、変更したコードが実際に動く場所まで操作して、 目に見えたものを捕捉する。その捕捉結果が証拠になります。テストや型チェックはCIの仕事です。 検証器の仕事は、本物の成果物が正しく振る舞うことを、 ユーザー（人間であれプログラムであれ）がそれに触れる境界で確認することです。

CLIなら表層はターミナル、サーバーならソケット、React アプリなら表層は レンダリングされたDOMです。だからこのシステムは、DOM自体を機械可読にし、 すべてのコンポーネントに「既知の状態で隔離してマウントされる手段」を与え、 判定を読み取るための構造化APIを公開します。

観点ユニットテスト検証（このシステム）
何が動くか関数。Node上で、モック付きコンポーネント。本物のDOM上で、本物の状態で
何を確認するか戻り値／モックの呼び出し実際にレンダリングされた内容と、その反応
誰が使うかCICI と ダッシュボード と AIエージェント — すべて同じコードパス
捕まえられる不具合ロジックのバグロジックのバグ、結合のバグ、コントラクトのずれ、a11yの退行
判定の形pass / failPASSFAILBLOCKEDSKIP

2 システムの解剖

図の読み方: コンポーネントがDOMコントラクトを出力し、スペックと検証器が 共有レジストリに登録され、ランナーがフィクスチャをマウントして検証器を走らせ、 構造化された VerifyResult を生成する唯一の実行パスになります。 4種類の利用者はすべてランナーを呼び出し、違うのは結果を 表示する／アサートする方法だけです。

ファイル構成

src/ ├─ features/todos/ アプリ本体 — data-verify-* コントラクトを出力する ├─ verify/ │ ├─ core/ │ │ ├─ types.ts VerifiableUnit, Fixture, Invariant, Verifier, Verdict │ │ ├─ contract.ts data-verify-* 用のヘルパー │ │ ├─ registry.ts ユニットと検証器の中央レジストリ + マニフェスト │ │ └─ runner.ts マウント → 操作 → 検証 → 判定 │ ├─ verifiers/ 差し替え可能: schema, invariants, dom-contract, a11y │ ├─ specs/ 1ユニットにつき1つの *.verify.ts（中央の /verify ディレクトリ） │ ├─ harness/ │ │ ├─ handle.ts window.__verify │ │ ├─ Dashboard.tsx /verify │ │ ├─ UnitPage.tsx /verify/:unit/:fixture │ │ └─ Report.tsx, Badge.tsx │ └─ matrix.test.ts CI: 全ユニット×フィクスチャを実行し、判定をアサートする └─ main.tsx 検証器とスペックをimportし、ハンドルを設置し、ルーティングする

3 DOMコントラクト（data-verify-*）

最下層のレイヤー。すべてのコンポーネントがルート要素に verifyAttrs({...}) を スプレッドし、自身の意味的な状態を表す data-verify-* 属性群を出力します。 スタイリングでも内部実装でもなく、意味です。 

// features/todos/TodoApp.tsx
<section
  className="todo-app"
  {...verifyAttrs({
    unit: "TodoApp",
    total: t.stats.total,   done: t.stats.done,   active: t.stats.active,
    filter: t.filter,      visible: t.visible.length,
  })}
>

これは次のようにレンダリングされます。

<section class="todo-app"
  data-verify-unit="TodoApp" data-verify-total="3" data-verify-done="1"
  data-verify-active="2" data-verify-filter="all" data-verify-visible="3">

これが重要な理由

DOM こそが 表層です。エージェントと検証器は、React の fiber を覗き込んだり CSSクラスから推測したりするのではなく、 readContract(root) → {unit, total, done, active, filter, visible} を読みます。コンポーネントの内部実装は丸ごと書き換えられます。状態管理ライブラリの変更、 スタイルの作り直し、リファクタリング — コントラクトが守られている限り、 すべての検証器は通り続けます。

ヘルパーは src/verify/core/contract.ts にあり、 verifyAttrs()（書き込み）、readContract()（ルートのコントラクトを読む）、 readAllContracts()（コントラクトを持つ子孫要素すべてを読む。リストや機能単位で便利） を提供します。

4 検証可能なユニット、フィクスチャ、不変条件

VerifiableUnit はモジュール性の単位です。単一のコンポーネント （kind: "component"）か、独自の状態を持つ機能スライス全体 （kind: "feature"）のいずれかです。 src/verify/specs/ の各スペックファイルが、ちょうど1つを登録します。 

// src/verify/specs/TodoItem.verify.ts（抜粋）
registerUnit<TodoItemProps>({
  id: "TodoItem",
  title: "TodoItem",
  kind: "component",
  render: (props) => createElement(TodoItem, props),
  propsSchema: z.object({ todo: TodoSchema, onToggle: z.function(), onRemove: z.function() }),

  fixtures: [
    { id: "active",     props: { todo: { text: "Buy milk", done: false, ... } } },
    { id: "done",       props: { todo: { text: "Ship it",  done: true,  ... } } },
    { id: "empty-text", probe: true, props: { todo: { text: "", ... } } },
    { id: "long-text",  probe: true, props: { todo: { text: "x".repeat(500), ... } } },
  ],

  invariants: [
    { id: "done-attr-matches-prop",
      check: ({ contract, props }) => contract.done === String(props.todo.done) },
    { id: "checkbox-state-matches",
      check: ({ root, props }) => root.querySelector("input[type=checkbox]").checked === props.todo.done },
    { id: "visible-text-never-empty",
      check: ({ root }) => root.querySelector(".todo-text").textContent.trim().length > 0 },
  ],
})

フィクスチャ

Fixture は、名前付きで再現可能なレンダリング構成です。 props を持ち、任意で命令的な act(ctx) ステップを持てます。 これはマウント後・検証前に実行され、「レンダリングして、Xをクリックして、それから検証する」 という流れをフィクスチャとして表現できます。 

// todos.feature.verify.ts より — 振る舞いのフィクスチャ
{
  id: "add-then-toggle",
  props: {},
  act: async (ctx) => {
    ctx.type("input[type=text]", "Ship it");
    ctx.click("button[type=submit]");
    await ctx.wait(16);
    ctx.click("li.todo-item input[type=checkbox]");
  },
}

🔍 probe は必須

probe: true が付いたフィクスチャは、敵対的／ハッピーパス外のケースです。 空文字、500文字のテキスト、空白文字だけの送信、矛盾した件数など。 経験則はこうです。「✅ばかりで🔍がないチェックリストは、ハッピーパスの再生にすぎない」。 CIのマトリクステスト（matrix.test.ts）は probe フィクスチャをひとつも宣言していないユニットを失敗させます。 ハッピーパスしかテストしていないユニットは出荷できません。

不変条件（Invariants）

Invariant は、マウントされたDOMに対する名前付きの述語です。 (ctx) => boolean | string という形をとり、true なら成立、 false か文字列なら違反（文字列はそのまま診断メッセージになります）。 不変条件は次のものを受け取ります。

rootユニットがマウントされている生きた HTMLElement
propsそのフィクスチャの props
contractパース済みの data-verify-* マップ — 通常はこれだけで足りる
fixtureフィクスチャそのもの（条件分岐用）

onlyFixtures: ["id", ...] を使うと、不変条件を特定のフィクスチャだけに 限定できます（例えば「追加後は total が 1」は add-then-verify フィクスチャでしか意味を持ちません）。

コンポーネント単位と機能単位

コンポーネント単位（Component unit）

TodoItem、TodoInput、TodoList、 TodoStats。スペックの視点からはステートレスで、フィクスチャが props を渡し、 不変条件がコントラクトにそれが反映されているかを確認します。 ひとつの部品を本当に隔離した状態でテストします。

機能単位（Feature unit）

todos.feature = TodoApp 全体。本物の状態を持ちます。 フィクスチャは act() に頼って操作を駆動します。不変条件が確認するのは 連携です。「TodoStats のコントラクトが TodoApp のコントラクトと一致する」 「表示件数がフィルタと一致する」「Todoを追加するとリストと統計の両方が更新される」。

5 差し替え可能な検証器

Verifier は、チェックの「種類」です。特定のコンポーネントには依存せず、 マウントされているユニット×フィクスチャが何であれそれを調べ、構造化された Check[] を返します。このデモには4つ同梱されています。

検証器何を確認するか失敗が意味すること
schemaフィクスチャの props がユニットの Zod propsSchema（.refine() ルールを含む）でパースできるかフィクスチャが「有効な入力」だと偽っている、または prop の型がずれた
invariants宣言されたすべての不変条件の述語を、生きたDOMに対して実行するコントラクトの主張が成立していない
dom-contractdata-verify-* コントラクトが存在し、自己識別できているか（data-verify-unit）表層が機械可読になっていない — エージェントは推測するしかなくなる
a11yボタンに名前があるか、入力にラベルがあるか、画像に alt があるかアクセシビリティの退行

インターフェースはごく小さいです。 

interface Verifier {
  id: string
  description: string
  run: (ctx: { unit, fixture, root, contract }) => Check[] | Promise<Check[]>
}

差し替え可能であることが肝

検証器とユニットは直交しています。新しい種類の検証 — ビジュアルスナップショット差分、パフォーマンス予算、i18n文字列のカバレッジ、 ダークモードのコントラスト — を追加するには、 src/verify/verifiers/ にファイルを1つ書き、index.ts で import するだけ。既存のすべてのユニット×フィクスチャに対して即座に実行されます。 コンポーネントの変更はゼロです。ユニット側は verifiers: ["schema", "invariants"] のように一部だけを選ぶこともでき、 省略すればすべてが適用されます。

6 ランナーと判定の分類

src/verify/core/runner.ts が唯一の実行パスです。それ以外はすべて、 単にこれを呼び出すだけです。runFixture(unit, fixture, opts?) は次のことを行います。

マウント画面外のコンテナを作る（または UnitPage から渡された可視コンテナを使う）→ createRoot → flushSync(render)。
操作（Act）フィクスチャに act() があれば、小さなドライバ（click、type、wait）とともに実行。type ヘルパーはネイティブの value セッターを使うため、React の onChange が発火します。
コントラクトを読むreadContract(container) → フラットな {unit, total, done, ...} マップ。
検証器を実行該当するすべての検証器が {unit, fixture, root, contract} に対して実行されます。例外はスタックトレースを証拠として付けた fail チェックになります。決して握り潰しません。
判定を算出fail チェックが1つでもあれば → FAIL。マウント/セットアップで例外 → BLOCKED。フィクスチャがゼロ → SKIP。それ以外は PASS。
VerifyResult を返す{unitId, fixtureId, verdict, checks[], domSnapshot, durationMs, timestamp, blockedReason?} — 完全にシリアライズ可能なJSON。

判定（Verdicts）

PASSマウントして操作し、すべてのチェックが成立した。「テストが通った」や「コードが正しそう」ではなく、表層があるべき振る舞いをしたということ。
FAILマウントして操作した結果、少なくとも1つのチェックが fail。checks[] 配列が、どれが・なぜ失敗したかを正確に教えてくれます。
BLOCKED変更が観測できる状態まで到達できなかった。マウントで例外、検証器が未登録、コンテナがない等。ユニットに対する判定ではありません。blockedReason がどこで止まったかを正確に示します。
SKIP実行時の表層が存在しない — ユニットがフィクスチャをゼロ個しか宣言していない。何も問題は起きておらず、観測すべきものがないだけです。

チェックのステータス

ok ✅ 確認できた   fail ❌ 観測した結果が誤っていた   warn ⚠️ 気になるが失敗ではない   probe 🔍 ハッピーパス外のケースが成立した

迷ったら FAIL

誤った PASS は壊れたコードを出荷してしまいますが、誤った FAIL のコストは 人間がもう一度見る手間だけです。だから検証器の例外は fail チェックになり、 曖昧な出力は生の証拠を添えて FAIL とし、warn／probe は 決して FAIL を PASS に格上げしません。

7 隔離されたルートとダッシュボード

/verify/:unitId/:fixtureId — 隔離マウント

ちょうど1つのユニットを、ちょうど1つのフィクスチャで、市松模様のステージ上に可視でマウントします。 その見えているマウントに対してすべての検証器を実行し、構造化されたレポートを下部に描画します。 ?chrome=0 を付けるとハーネスのヘッダーとレポートが隠れるので、 エージェントはコンポーネントだけのきれいなスクリーンショットを撮れます。

これが求めていた「隔離されたレンダリング先」です。アプリのシェルもプロバイダもノイズもありません。 このページは JSON の結果を <script id="verify-result-json" type="application/json"> にも書き込むので、 DOMしか読めない（JSの評価ができない）エージェントでも構造化された出力を得られます。

/verify — ダッシュボード

登録されたすべてのユニット、そのフィクスチャ（🔍マーカー付き）、不変条件、 どの検証器が適用されるかを一覧表示します。「Run all」はマトリクス全体を 画面外で実行し、判定グリッドを描画します。サマリーバー （✅ n ❌ n ⛔ n / total）は data-verify-summary のJSONとしても 出力されます。「Raw manifest」の開閉パネルでは、__verify.manifest() から エージェントが見るものをそのまま確認できます。

8 window.__verify — エージェント用ハンドル

起動時に installVerifyHandle() によって設置されます。これは 検証器自身のためのプログラム向け表層です。AIエージェント、Playwright、 あるいは devtools を開いたあなたが使います。

メソッド戻り値用途
manifest()VerifyManifestEntry[]すべてのユニット、そのフィクスチャ（probeフラグ付き）、不変条件、適用される検証器、そして隔離URLを返す route(fixtureId) 関数を発見する。
current()VerifyResult | null現在マウントされている /verify/:unit/:fixture の構造化された結果を読む。それ以外の場所では null。
runAll()Promise<VerifyResult[]>ページを離れずに、マトリクス全体をヘッドレス（画面外マウント）で実行する。ダッシュボードのボタンやCIと同じコードパス。
version"1.0"パースする前に、エージェントがプロトコルの形を確認できるようにする。
 
// AIエージェントがやること — DOMスクレイピングもセレクタの推測も不要
const manifest = window.__verify.manifest()
// 機能スライスを選ぶ
const app = manifest.find(m => m.unitId === "todos.feature")
location.href = app.route("add-then-toggle")   // → /verify/todos.feature/add-then-toggle
// ... 遷移後 ...
const r = window.__verify.current()
r.verdict        // "PASS"
r.checks         // [{verifier:"invariants", status:"ok", label:"after add+toggle, done=1"}, ...]
r.domSnapshot    // {unit:"TodoApp", total:"1", done:"1", active:"0", filter:"all", visible:"1"}

9 1本のパイプライン、3種類の利用者

構造上もっとも重要な性質がこれです。VerifyResult を生み出す方法は ちょうど1つしかありません — runFixture() です。 3種類の利用者の違いは、それをどう取得して提示するかだけです。

利用者入口マウント方法提示方法
人間（ダッシュボード）/verify → 「Run all」ブラウザ内、画面外判定グリッド + ユニット別テーブル
人間（1件に集中）/verify/:unit/:fixtureステージ上に可視でライブレンダリング + レポートカード + JSONシンク
AIエージェント / Playwrightwindow.__verify画面外（runAll）または可視（遷移 + current）生の VerifyResult JSON
CIbun run verify → matrix.test.tsjsdom、ヘッドレスユニット×フィクスチャごとの vitest の pass/fail

パイプラインが1本なので、退行はどこでも同一に現れます。 「CIでは通るのにエージェントには FAIL に見える」ということは起こり得ません。 まったく同じ関数呼び出しなのです。

10 エンドツーエンドのウォークスルー

todos.feature / whitespace-submit で何が起きるかを追ってみます。 これは空白文字だけを入力して強制的に送信し、Todoが1件も作られていないことを アサートする🔍probeです。

スペックが登録されるtodos.feature.verify.ts が registerUnit を呼び、フィクスチャ {id:"whitespace-submit", probe:true, props:{}, act: "   " を入力して送信} と不変条件 whitespace-blocked: contract.total === "0" を登録します。
利用者がランナーを呼ぶダッシュボードの「Run all」／__verify.runAll()／vitest が、それぞれ runFixture(unit, fixture) を呼びます。
マウント + 操作TodoApp が空の初期状態でレンダリングされます。act が入力欄に " " を入力し（ネイティブセッター → React の onChange が発火）、フォームに submit イベントをディスパッチします。
コントラクトを読むuseTodos.add() がトリムして空を拒否するため、DOMには data-verify-total="0" が表示されています。
検証器が実行されるschema ✅ props は有効 · dom-contract ✅ コントラクトあり · a11y ✅ 入力にラベルあり · invariants が whitespace-blocked を含む6つの述語を実行 → probe 🔍。
判定fail チェックなし → PASS。結果: {verdict:"PASS", checks:[...11], domSnapshot:{unit:"TodoApp", total:"0", ...}}。

意図的な失敗: TodoStats / inconsistent-counts

この probe は {total:10, done:3, active:4} を渡します。Zod の .refine(d => d.total === d.done + d.active) が失敗し → schema 検証器が fail チェックを出し → 判定は FAIL になります。そしてマトリクステストは これが FAIL であることをアサートします。このフレームワークが真実を確認するだけでなく、 嘘を見つけ出せることの証明です。スキーマを緩めて「直して」しまうと、CIが壊れます。

11 拡張: 新しいユニットと検証器

検証可能なユニットを追加する

// src/verify/specs/MyThing.verify.ts
import { registerUnit } from "../core/registry"
import { MyThing } from "../../features/.../MyThing"

registerUnit({
  id: "MyThing", kind: "component",
  render: (p) => <MyThing {...p}/>,
  propsSchema: z.object({...}),
  fixtures: [
    { id: "default", props: {...} },
    { id: "edge", probe: true, props: {...} },
  ],
  invariants: [{ id: "...", check: ctx => ... }],
})
// そのうえで specs/index.ts に import "./MyThing.verify" を追加

検証器の種類を追加する

// src/verify/verifiers/perf.ts
import { registerVerifier } from "../core/registry"

registerVerifier({
  id: "perf",
  description: "レンダリングを16msの予算内に収める",
  run({ root }) {
    const n = root.querySelectorAll("*").length
    return [n < 500
      ? { verifier:"perf", status:"ok",   label:`DOM size ${n}` }
      : { verifier:"perf", status:"warn", label:`DOM size ${n} > 500` }]
  },
})
// そのうえで verifiers/index.ts に import "./perf" を追加
// — 既存の全ユニット×フィクスチャに対して即座に実行される

どちらもコンポーネントに手を入れる必要はありません。これが「モジュール性がある」という 主張を具体的な形にしたものです。

12 設計原則のまとめ

  1. 内部実装ではなく表層。 レンダリングされたものを検証する。 DOMコントラクトは、コンポーネントと検証器のあいだのABIである。
  2. パイプラインは1本。 runFixture() が判定を生み出す唯一の方法。 ダッシュボード、エージェント、CIはそのビューにすぎない。
  3. すべてを構造化する。 マニフェスト、結果、チェック、スナップショット — すべてJSON。AIエージェントがスクレイピングや推測をする必要は一切ない。
